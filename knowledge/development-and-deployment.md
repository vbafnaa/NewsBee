- Use Node.js 24 and npm 11. Run `npm ci` in each app. From the repository root, `npm --prefix apps/journalist-site run local` starts both apps, local MongoDB, and the scheduler. See [local setup](../README.md#run-locally) for model setup and ports.
- The local stack's [typed review fixtures](../apps/journalist-site/scripts/local-review-fixtures.ts) seed generated-shaped drafts, real approval/publish artifacts, ready synthetic locations and separate editor assignments. `NEWSBEE_LOCAL_REVIEW_SCENARIO` selects `source-runs` (default) or `blocked-generation` without competing active workflows. Setup accepts only loopback MongoDB and preserves initialized fixtures; use fresh local data/database names for clean reviews. The README documents isolated ports and reserved `.test` media mocking.
- From the root, use `npm --prefix apps/journalist-site test`, `npm --prefix apps/journalist-site run lint`, and `npm --prefix apps/journalist-site run build` for journalist changes. Use `npm --prefix apps/reader-site run check` and `npm --prefix apps/reader-site run build` for reader changes.
- For the focused control/source-field geometry regression, run `node --test apps/journalist-site/pipeline/tests/workspace/item24-geometry.test.mjs` from the root (Windows shells use backslashes). It uses installed headless Edge, or `NEWSBEE_TEST_BROWSER`, and skips when no browser is available. The reconstructed component fixture reproduces nested clipping and measures fields/focus outlines at 761, 768 and narrow desktop widths; it does not establish authenticated-app U01 acceptance, physical mobile behavior or real keyboard traversal.
- Admin Overview prioritizes the readiness queue and compact campaign counts instead of tutorial/navigation cards. Optional location onboarding is collapsed except for exact requested-location deep links. Healthy execution copy is omitted only in this compact view; loading, blockers, reconnect guidance and failures stay exposed. Readiness rows give copy the full available width, stack wrapped actions below it, and avoid repeating the same blocker detail. Validate populated alerts and long source URLs at narrow and intermediate widths, not an empty directory or nonshrinking buttons alone.
- [Root Vercel config](../vercel.json) routes `/` to Next.js and `/reader` to Astro and defines the journalist queue trigger. Publication email signup, email preview and sending are unavailable: the HTTP boundaries return 503 before subscription, campaign or delivery writes. Do not schedule delivery. Historical consent, signed preferences and unsubscribe remain supported; private web preview is independent. Both app deployment rules remain `main`-only. Follow [the deployment policy](../AGENTS.md) and consult the [deployment guide](../Docs/deployment.md) for environment settings.
- [Journalist middleware](../apps/journalist-site/middleware.ts) explicitly uses `config.runtime: "nodejs"` (supported by the locked Next.js 15.5 version). Vercel services reject Edge Function output, including middleware's default Edge runtime. Keep the trusted return-path header and matcher intact; do not remove middleware or split the service to bypass the build failure.

## Full-snapshot restore

- [Site backup](../apps/journalist-site/app/site-backup/site-backup.tsx) remains a **full** replacement, including accounts, passwords, role/membership assignments, publication ownership and ordinary audit history. It is not a content-only import. Retain a secure pre-restore export separately. The owner must close maintenance, drain writers, and separately type `REPLACE ALL SITE DATA` and `ROLL BACK ACCOUNTS AND GOVERNANCE`. Both the staged-stream and direct JSON imports enforce this in the destructive service.
- Stop older deployments, local scripts, database administration jobs and other uninstrumented writers before closing maintenance. Current application writes use epoch-pinned `fencedDatabase(db)` handles from `getDatabase`, `getMongoDatabase` and `readerDatabase`; this includes direct Reader campaign signups and submissions. `withSiteWriter(db, work)` holds admission across admin/publication handlers, workers, provider delivery, artifacts and transaction commit/abort. New side-effecting background entrypoints must hold it for their full lifetime, not just check maintenance once. Do not write through a raw Mongo client or retain unfenced artifact stores in application code.
- Maintenance acquisition and writer admission atomically update the same deployment-authority document. Closing admission increments its epoch, revokes prior sessions (including previously revoked owner sessions that must never regain access), blocks new writers/claims and lets admitted writers finish while remaining counted. The owner must sign in again through verified Google to continue maintenance. Restore requires zero writers and rejects active queue/provider/upload authority before deleting any artifact. Writer tokens **never expire automatically**: elapsed leases are not proof that a process stopped. Old handles cannot write after reopening.
- `_newsbee_restore_state` and append-only `_newsbee_restore_evidence` are independently retained deployment authority in the destination database. They, the entire reserved `_newsbee_restore_*` namespace, system collections and backup staging stores are excluded from export/replacement and rejected if supplied by an archive. Protect these stores with the destination database's backup/access controls; they are not an off-database disaster-recovery backup.
- Evidence records owner, archive SHA256, source date, affected collection names, restore reference and start/completion/failure outcomes, never the archive contents or credential links. `readRestoreEvidence(db): Promise<RestoreEvidence[]>` returns the latest 20 safe projected events for already owner-authorized callers. Its `at` is a BSON `Date` (ISO-8601 over JSON), **not seconds**; `sourceCreatedAt` is the archive's ISO string. Types and collection constants are exported from [the shared maintenance module](../shared/restore-maintenance.ts).
- Every restore attempt that acquires destructive ownership rotates an independently retained random identity generation before replacement. Existing sessions and archived outstanding signup/recovery links cannot revive even when account session versions roll backward. Restored job/worker/video/email authority is quarantined rather than resumed: original status/claim/lease fields are retained under `restore_quarantine`, jobs are cancelled/failed, active generations/campaigns are blocked, and runs require deliberate fresh admission. This does not cancel already-submitted work at external providers or undo previously sent mail.
- Success stays `restored` with maintenance **closed** until the configured owner reviews evidence and deliberately reopens. Failure/abort stays `failed`; only a successful known-good restore permits reopening. Sign in again through verified Google using the exact `NEWSBEE_OWNER_EMAIL` to recover access even if account collections are missing or partially replaced; password sign-in is unavailable while closed. OAuth configuration and owner email remain deployment configuration, never archive authority.
- A terminated process may leave `restoring` or persistent writer tokens. There is intentionally no timed unlock or web force-open. An infrastructure operator must first stop/verify termination of **all** potential old writers and the restore process, preserve the authority/evidence documents and partial destination, then record an independent recovery event and reconcile the exact stranded tokens/restore reference in the destination authority to `failed` (or `draining` only when no destructive attempt began). Never delete/reinitialize the authority stores or change the identity generation backward. The configured owner can then upload/retry a known-good snapshot while closed; staged uploads are separate temporary storage and do not reopen application writes.
