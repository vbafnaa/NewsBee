# Local Facebook group collector

A standalone local dashboard for authorized group-post collection. It is **not connected to Newsbee** and never publishes collected material. The dashboard listens only on `127.0.0.1:4317` (override with `NEWS_COLLECTOR_PORT`). Storage is JSON in `.local/data/collector.json`, ignored by Git.

## Before using it

Only collect from groups for which you have permission from the group and applicable authorization from Meta. Group-admin approval alone is not Meta authorization. Facebook no longer provides a general Groups API; this browser-viewing approach is best-effort and may be restricted by Meta's terms. Do not create deceptive identities or bypass authentication, challenges, or access controls. Review relevant privacy requirements before using or sharing any posts. The tool does not supply credentials or automate sign-in.

## Local setup

1. Install [Node.js 22 or newer](https://nodejs.org/) and Chrome (or Edge/Chromium). In Chrome, install the official [Playwright Extension](https://chromewebstore.google.com/detail/playwright-extension/mmlmfjhmonkocbjadbfplnigmagldckm) from the Chrome Web Store, in the browser profile you intend to use. Sign in to Facebook **manually** in that profile. If the Web Store is blocked, resolve browser policy with your administrator rather than bypassing it.
2. Click the extension icon or open its status page and copy its `PLAYWRIGHT_MCP_EXTENSION_TOKEN` value. Start a **new terminal** with the token available to the collector process. For example, in PowerShell, set it for this terminal (replace the placeholder locally):

   ```powershell
   $env:PLAYWRIGHT_MCP_EXTENSION_TOKEN = 'paste-token-locally'
   ```

   Keep this token private. Never put it in a tracked file, issue, screenshot, log, or exported JSON. The extension can also prompt for connection approval without a token, but unattended scheduled collection requires a token. If multiple Chrome profiles have the extension, use the matching profile's token and optionally set `PLAYWRIGHT_MCP_PROFILE_DIR_NAME` to the directory name shown at `chrome://version`.
3. From this repository, install and build the pinned local Playwright CLI and dashboard:

   ```powershell
   cd incubating-connectors\facebook-group-collector
   npm ci
   npm run build
   npm start
   ```

   The collector uses `node_modules\.bin\playwright-cli --extension=chrome`; **you do not need to install Playwright MCP separately**. Keep this terminal and the signed-in browser open. Open `http://127.0.0.1:4317` (override the loopback port with `NEWS_COLLECTOR_PORT`). Use **Settings** in the left navigation for Chrome connection, collector and queue status, scheduler state, and Connect Chrome / Pause scheduler controls. Press **Connect Chrome** if needed, and approve any browser connection prompt. If Chrome reports `ERR_BLOCKED_BY_CLIENT`, check that the official extension is enabled and allowed by your browser policy. If it reports an unsupported protocol version, update the extension and the pinned `@playwright/cli` dependency together, reinstall with `npm ci`, and rebuild. If the status remains disconnected, confirm that the token exists in the **process** environment (a user variable added after a terminal was opened is not inherited by it), that the extension is installed in the selected profile, and that Chrome is running. Never print the token while troubleshooting.
4. Choose **Add a group**, provide a permitted Facebook group URL and display name, then choose **Queue run** from the separate collection panel on its group detail page. Manual runs let you select a lookback of 1 hour (default), 7 days, or 30 days. Each run opens and closes two scan tabs in sequence: a full `sorting_setting=CHRONOLOGICAL` scan using the selected publication-time cutoff, then `sorting_setting=RECENT_ACTIVITY` until ten distinct original posts are accepted or the feed stops yielding posts (also used by the dashboard's View on Facebook link). It may briefly open additional tabs to resolve share links for posts without exposed IDs. The second step does not filter by age, even when posts predate the manual lookback or scheduled cutoff; it still records a publication time when available. Duplicate posts from the two steps are merged. Complete sign-in or challenges manually. Each group starts with an automatic daily schedule at 09:00 in the service machine's local timezone. In **Group settings → Automatic collection**, choose every hour (at the start of each hour), every day or every week; select a local time for daily/weekly and a weekday for weekly, then save. The next run is displayed there. Leave the service and signed-in Chrome with its extension running: every minute the service checks due groups and connects to Chrome automatically when collecting, without a dashboard click. A missed occurrence while the service was off is queued once after restart; it does not backfill every missed date. Pausing the scheduler prevents automatic queuing without cancelling manual runs; up to 50 pending runs are queued and processed serially. Manual work overlapping a scheduled time does not start a duplicate. Stop the service with Ctrl+C. `npm run dev` builds the UI and starts the same local server.

## Group management, saved posts and export

**All groups** lists your configured groups. Select a group to view its details: edit its display name, open its Facebook URL, queue a run, browse **all saved posts** (50 per page), and inspect its collection history. Select a run's **View results** to switch between **Run activity**, **Captured posts**, **Run diagnostics** (including the downloadable JSON attachment), and **Encountered articles** (raw captures) tabs. The diagnostics attachment includes bounded raw feed HTML and visible text, so it can contain private content; keep it local. New runs do not take screenshots. When publication time remains unknown, **Captured posts** shows the complete rendered post card HTML as escaped text in its run snapshot only; it is not copied to **All saved posts** or the post export. Historical screenshots remain available in both views. Existing screenshots stay local under `.local\data\screenshots\<run-id>` while referenced by either a run snapshot or a saved post; they are removed after both references are cleared (or after a date is subsequently recovered and no run retains the image). On startup, existing undated saved posts are linked to screenshots in retained run snapshots when the image file still exists; runs predating screenshot capture have no images, and a missing screenshot does not imply the time was found. Captured HTML and historical screenshots may include visible replies or member details, so keep them local and do not share them without permission. Runs interrupted by a restart are marked failed and queued runs resume. Older runs created before per-run snapshots cannot be reconstructed.

Group settings can configure automatic hourly, daily or weekly collection. Scheduled runs require the service to stay running, an available signed-in Chrome extension session, and a token in the service process environment. Scheduling is in-process; it does not install an operating-system background service or start Chrome for you. Each queued run attempts to connect when it starts; if a cached Chrome attachment has gone stale, the collector reattaches and retries opening its tab once. If Chrome or its extension remains unavailable before the first scan, the run fails. During a scan, completed scan results are sent to a short-lived, randomly keyed localhost receiver in the app process; on a browser command failure or timeout, the run retains those posts and shows `partial_disconnect` instead. Its unfinished portion is not considered covered by the next scheduled cutoff, so a later run re-scans it and deduplicates saved posts. A disconnect before the first checkpoint cannot preserve posts, and an interrupted run does not resume at the exact scroll position. The temporary receiver closes when the browser command completes or fails; run snapshots remain local.

Group settings can permanently **Clear history** (queued runs, snapshots and diagnostics) or **Clean saved posts** by an optional inclusive local calendar-date range. History uses the queued date; saved posts use their first observed date. Leaving both dates blank clears all dates for that group. Removing posts also removes matching posts from saved run snapshots, not other groups' posts. Clearing all posts cancels queued runs. Neither action can run while a collection is active for that group. **Delete group and all its data** removes its settings, posts, run history and diagnostics after confirmation. These actions cannot be undone.

The **Export posts** page lets you select a group and optional inclusive observed-date range, then download a JSON file with group metadata, export timestamp, time range and saved posts. An empty date range exports all saved posts for that group. Export does not include run diagnostics. The file may contain private group content: obtain permission before uploading it elsewhere and store it securely. Local API equivalents include `DELETE /api/groups/<id>`, `DELETE /api/groups/<id>/runs`, `DELETE /api/groups/<id>/posts` (the clear endpoints accept optional ISO-8601 UTC `from` inclusive and `to` exclusive query parameters) and `GET /api/export?groupId=<id>&from=<ISO>&to=<ISO>`. Mutating endpoints require the dashboard's local request token.

Saved posts and run history are **not automatically deleted**; use the date-range controls to remove them. The first (chronological) step of manual runs targets posts published within the selected 1-hour, 7-day, or 30-day lookback (default 1 hour). Scheduled first-step scans start from the previous completed run's start time for that group, or the last seven days if no prior completed run exists. The recent-activity second step scrolls until it accepts ten distinct original posts regardless of timestamp, or stops when the feed yields no more new posts or reaches its safety limit; an older post can therefore appear in a one-hour run. Failed runs do not advance that cutoff. A partial run does advance it, so review incomplete scans before relying on incremental coverage. These are collection windows, not storage expiry. Data is stored in ignored `.local\data\collector.json`; maintain backups and manage its size and access yourself. Removing `.local\data` deletes all local collection data. The collector never uploads posts automatically.

### Optional Gemini layout hints (Google AI Studio)

Create a key at [Google AI Studio](https://aistudio.google.com/apikey). The collector reads `incubating-connectors\facebook-group-collector\.local\config.env` on startup. Create this **untracked, ignored local file** with the following contents, replacing the placeholder with your own key (do not add quotation marks):

```dotenv
GEMINI_API_KEY=your-key-here
GEMINI_LAYOUT_ASSIST=1
```

Alternatively set these in the environment of the terminal launching `npm start`; existing process environment values take precedence over the file. Keep `config.env` private, never commit, upload, or share it. Restart the app after changing the file or environment; a running process does not reload settings. To turn hints off, set `GEMINI_LAYOUT_ASSIST=0` and restart. The key is never written to collector JSON or displayed by the dashboard. On runs with zero identifiable posts, the optional Gemini API receives **only bounded aggregate element counts** from the scrolling feed (such as number of articles, comment-labeled articles and message containers), never post/comment text, group URLs, screenshots, page markup, credentials or links. The hint appears in the completed run's reason. Network failure leaves local extraction unchanged. Gemini cannot recover unseen posts or override local post validation. Each analyzed run makes one potentially billable `gemini-3.1-flash-lite` API call; review [Gemini pricing](https://ai.google.dev/gemini-api/docs/pricing) and Google's data-handling terms before enabling it.

The per-group run detail view's **Run activity** is a chronological, monospace developer log that refreshes every three seconds during collection. It includes connection and scan stages, elapsed-time heartbeats every ten seconds while scanning, safe aggregate layout counters at scan completion, saved-post counts, and final status. The log keeps the latest 100 entries in memory, resets on restart, and never prints raw browser output, page text, links, credentials or per-scroll counts (the browser command returns only after its scan finishes). Completed run status and counts remain in the group's **Collection runs**. `partial_comments_only` and `partial_feed_unloaded` are classified locally, with or without Gemini: links within comment-labeled articles cannot verify original post bodies, and empty placeholders cannot establish that post bodies are missing. Separate `commentLinksSeen` and `postLinksSeen` counters make this difference visible without recording links.

The first step creates a dedicated chronological tab, waits up to 15 seconds for placeholder feed articles to hydrate and briefly lets the initial feed settle, expands **See more** in original post cards as they appear while scrolling (including unmarked cards and a retry when a card arrives after the first expansion pass, without opening comment threads), scrolls through the rendered feed toward the selected publication cutoff, then closes that tab. It stops at the first dated post older than the cutoff (without inspecting later cards in that scan), after three scans with no new posts when scrolling has stalled (or ten scans without new posts even if the page still scrolls), or at the safety limit of 44 chronological scans / 250 posts. The second recent-activity tab scrolls past rejected cards and duplicates until it accepts ten original posts without checking age. It stops after five consecutive scans with no new posts when scrolling has stalled (or ten scans without new posts even if the page still scrolls), or at the safety limit of 44 scans; if fewer than ten are available, its diagnostic step reports `partial_fewer_posts` (or `partial_limit` when capped). Run diagnostics identify both sorts and retain their step statuses. If the second step fails, the first step's posts are saved with `partial_second_step` status. A dated post older than the selected window ends the chronological step immediately but may be included by the recent-activity top-ten step; saved posts are retained until explicitly cleared. Undated posts have **unverified age** and may be included even when outside the selected lookback; a `partial_unknown_time` result is not proof of time-window coverage. The dashboard labels their publication time as unknown and shows the separately recorded observation time, which is not evidence that the post was published within the lookback. It stores the original post body, displayed comment count and reaction total when available, recognizable reaction types (Like, Love, Care, Haha, Wow, Sad, Angry), and per-type counts only when explicitly exposed. Facebook may put the displayed reaction total inside its **Like** action, the comment count inside **Leave a comment**, and individual reaction counts in labels such as **Like: 23 people**; these are read from the original card, not from reply controls. Missing counts are unknown, not zero. It also stores the original post link when exposed by the card, including a unique matching group-post ID in a nested reply's `comment_id` URL when the post header only points to the group. For cards with no exposed post ID, it retries that card's Share dialog across scans and follows its Facebook share link (including `l.facebook.com` redirects) in a temporary tab, keeping the numeric permalink only when it resolves back to the same group; ambiguous or unrelated links are not used. It stores external source links if present, an observed time, and the original post header's displayed absolute or relative time when recognizable. The displayed label is saved separately; parseable labels (including an accessible label referenced by an original-header link or its visually ordered, per-character date spans when Facebook inserts hidden decoys) are resolved into a publication timestamp at collection time, while reply timestamps and dates mentioned in the post body are excluded. The collector briefly retries an undated initial card while its header hydrates, and scrolls virtualized cards back into view before hovering SVG-only original-header time links (including a direct hover when their hit-tested area is covered), then restores the feed scroll position; each undated card gets at most two hover passes (including post permalinks) to read their publication-time tooltip when no text or accessible label is present. Later scans can add a newly available original-header date. If the feed does not display a card or its tooltip, publication time remains unknown rather than being inferred from comments or observation time. The dashboard displays each post's numeric Facebook post ID when a usable group permalink exists. Repeat captures of that ID refresh available comment/reaction statistics and fill missing original publication metadata; existing publication dates, initial text, source links and observation time remain unchanged. A previously truncated linkless teaser can be replaced by a later expanded capture of the same opening text; historical run snapshots still reflect what was captured at the time. If Facebook exposes no post ID, a local fallback ID hashes the group and text to avoid duplicates across shifting relative timestamps. Identical linkless posts can be merged, and an edited linkless post may have a different fallback ID. The accepted-post archive never stores comment text, expands hidden comment threads, or collects member lists, profile details, or media files; raw diagnostic captures may include visible comments and member details from the rendered feed. Older locally saved comment text is removed from the JSON store on startup. Facebook may render original post bodies in feed cards without an article role while giving comment replies article roles. The collector accepts those cards only when their original message element is present outside comment articles; it does not turn comments into posts. A genuinely comment-only feed reports `partial_comments_only`. Older saved entries made before this change are labeled unverified until refreshed or cleared; entries without an identifiable post body are skipped rather than presenting comments as post content. Feed ordering, missing timestamps, layout changes, and lazy loading may cause missed, undated, or truncated posts or comments. A `partial_*` run status is expected and **does not guarantee complete coverage of the selected window**; `partial_unknown_time` flags unverified dates and `partial_limit` flags the safety cap. Feed articles without readable original-post text are skipped. A usable group permalink is optional: linkless posts receive a local group-and-content hash for deduplication, so identical text can be merged and edits may appear as distinct captures. A post without a link cannot be opened on Facebook from the dashboard until a verified original URL is supplied. In **All saved posts**, use **Add verified original link** on a local-fallback post to attach its Facebook group-post URL; the archive and matching historical run snapshots are updated together. Never guess a post URL from a date, a photo ID, or a reply about a different post. When a later verified capture matches a linkless saved post by group and body, its archived permalink also backfills matching historical run snapshots; other older linkless posts still require a verified original URL.

JSON writes use atomic replacement and a single-instance lock file. Do not run two instances against the same directory; after an unclean crash, verify no collector process is still running before removing `.local/data/collector.lock`. Saved posts and run history are kept until manually cleared; startup and periodic cleanup remove legacy sensitive comment text but not saved records. Purging all of a group's posts cancels its pending runs; the next scheduled time is unchanged. Deleting `.local/data` removes all local collector data. Temporary Playwright CLI output and snapshots are removed after each command; persisted run diagnostics remain in local JSON until manually cleared. Do not upload local browser artifacts or store a token in the repository. Rotate any extension token previously exposed in logs.

## Diagnosing missed posts with the signed-in browser

1. Keep the service and manually signed-in Chrome profile running. On the affected group's page, queue a manual one-hour run (or inspect its next scheduled run), and open **View results** after completion. Note its run ID, status, saved-post count and scan counters. Compare with a visible original post in the group, not a comment/reply. The first scan requests `sorting_setting=CHRONOLOGICAL` and applies the selected publication-time cutoff, although feed ordering is not a guarantee of date coverage. The second scan requests `sorting_setting=RECENT_ACTIVITY` and scrolls for up to ten accepted original posts without an age filter.
2. In run diagnostics, compare `articles`, `commentArticles`, `candidateItems`, `newItems`, `postLinks`, and the reason/status across scans. A feed with only comment-labeled articles can still have original bodies in an unmarked parent card; zero message markers alone does **not** prove there are no posts. `partial_feed_unloaded` indicates placeholders; `partial_comments_only` means no verified original bodies; `partial_unknown_time` means some accepted posts lack usable publication times. The 44-scan / 250-post cap may also prevent complete coverage.
3. If the counts contradict what Chrome displays, use the same authorized browser connection for a temporary Playwright CLI inspection. From `incubating-connectors\facebook-group-collector`, run `node node_modules\@playwright\cli\playwright-cli.js -s=diagnose-group attach --extension=chrome`, then `... -s=diagnose-group tab-new "https://www.facebook.com/groups/<group-id>?sorting_setting=RECENT_ACTIVITY"`. Inspect DOM **structure only**: number of `[role="feed"]` children, comment-labeled `[role="article"]` nodes, original `[data-ad-preview="message"]` nodes, and `[dir="auto"]` body leaves outside comment articles. Do not print post text, HTML, URLs containing account data, tokens, or browser snapshots. Close only the diagnostic tab and session with `... -s=diagnose-group tab-close` and `... -s=diagnose-group close`; never close another user's tabs.
4. After an extractor change, run `npm test` and `npm run build`, queue a fresh live run, and confirm the new run saves original bodies without comments masquerading as posts. Verify its cutoff and status, not just aggregate saved-post totals (deduplication may keep totals flat). Keep any temporary inspection scripts in ignored `.local\browser`, delete them afterward, and never share the raw diagnostics attachment: it can contain private posts, comments, and profile details.
